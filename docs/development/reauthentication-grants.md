# Réauthentification transactionnelle — jalon 4.3C

Jalon terminé et commité (`7548633`), sans endpoint ni autorisation E2EE. SEC-CRYPTO-002 et SEC-CRYPTO-003 restent ouverts. La réauthentification prouve la connaissance du mot de passe serveur ; elle ne prouve pas la possession de l'identité cryptographique commune.

## Audit et composition

4.3A fournit `verifyPassword` asynchrone et ses erreurs assainies. 4.3B authentifie les jetons sous `Account FOR UPDATE`. 4.2B préparait les mutations puis ouvrait toujours sa transaction ; cela empêchait une consommation atomique externe. L'extraction minimale ajoute `preparePasswordChange` et `executeInTransaction` au repository du coffre, en conservant `rewrapPassword`, ses paramètres, ses validations, les reçus et les clés HMAC. Ces points d'entrée de stockage exigent un appelant de confiance détenant le verrou ; ils ne sont pas une API d'autorisation.

Le contrôle de session sous transaction et la règle d'expiration sont extraits sans changer leur comportement. `PostgresReauthentication` orchestre uniquement le changement ordinaire de mot de passe ; aucun callback de mutation arbitraire n'est exposé par cette composition.

## Grant et intention

La migration `20261115020000_reauthentication_grants` crée `ReauthenticationGrant` et un index unique composite de session. Le grant référence exactement compte, session et appareil via une clé étrangère composite. Il conserve un UUID public, SHA-256 du secret, type d'opération, UUID d'opération, empreinte d'intention, révision d'identifiants, création, expiration et consommation nullable. Les contraintes imposent empreintes de 32 octets, révision positive, dates finies, durée exacte de cinq minutes et consommation dans cet intervalle. Un trigger interdit toute modification d'identité et toute annulation ou modification d'une consommation acquise. Aucun statut supplémentaire. Les anciennes migrations restent inchangées.

Le jeton `r1.<UUID v4>.<secret Base64url canonique>` utilise une génération indépendante de celle des sessions, avec 32 octets CSPRNG Node. Le parseur commun est explicitement appelé avec `r1` et refuse `s1`, identifiant seul, padding et bits non canoniques. Comparaisons d'empreintes avec `timingSafeEqual`. Aucun jeton brut ni mot de passe dans les tables ou reçus ; aucun log émis. L'effacement des buffers est effectué au mieux, sans promesse sur les chaînes JavaScript.

L'intention de préparation V2 est le SHA-256 d'un tuple JSON à positions fixes, avec domaine/version, type `ordinary-password-change`, version transport, compte, identifiant d'opération, coffre, deux préconditions CAS, digest de la publication candidate, digest et génération de départ, et PHC exact du nouveau vérificateur préparé. Les validateurs existants sont réutilisés ; le digest candidat est recalculé sur ses octets. Seule l'empreinte est persistée dans le grant : ni mot de passe, ni copie du PHC. Le tuple transitoire engage le PHC salé complet ; ce n'est pas un SHA-256 simple du nouveau mot de passe. Toute substitution, y compris par une autre dérivation du même mot de passe avec un autre sel, est refusée avant consommation. Le domaine passe à `bunny-talks/reauthentication/intent/v2` ; les anciens grants expérimentaux V1 ne sont pas reconnus. Aucun champ ou migration supplémentaire n'est nécessaire, et aucune ancienne migration n'est modifiée. Cette liaison engage une publication chiffrée, sans authentifier son manifest côté serveur.

Le HMAC historique de 4.2B est inchangé et reste distinct de cette liaison : elle engage les données préparées exactes, y compris le vérificateur aléatoirement salé. Un nouveau calcul de vérificateur peut donc changer l'identité interne de rejeu. Cette composition reste une primitive interne : le futur service applicatif de confiance doit calculer le PHC avec `createPasswordVerifier`, puis conserver cette préparation exacte pour l'émission, la mutation et la reprise. `issuePasswordChange` exige maintenant le `PreparedPasswordChange` complet, validé et engagé avant le premier `await` ; un PHC fourni directement par un client HTTP ne doit pas constituer cette préparation serveur. Le composant de confiance doit associer correctement le mot de passe à l'enveloppe candidate ; le serveur ne peut pas prouver cette correspondance E2EE. Le vérificateur préparé doit respecter le profil serveur reconnu.

## Émission et consommation

`issuePasswordChange(sessionToken, password, request, preparation)` valide la session, lit le vérificateur et sa révision, puis appelle réellement Argon2id hors transaction. Après calcul, un verrou exclusif de compte est acquis. La session, l'appareil, le vérificateur exact et sa révision sont relus ; tout changement refuse l'émission. L'appareil doit aussi avoir un `authorizedAt` non nul à cet instant, sinon l'émission est refusée. L'échéance de cinq minutes est établie après acquisition du verrou. Aucune assertion `passwordVerified` ni simple identifiant n'accorde de preuve.

`changePassword(sessionToken, grantToken, request, preparation)` prépare l'opération puis, sous le même verrou exclusif de compte, revalide session, appareil, secret de grant, liaisons et intention (dont le PHC exact). Un `authorizedAt` absent refuse la composition, même avec un grant valide ou déjà consommé ; l'appareil révoqué reste refusé. Pour une nouvelle mutation, la révision doit correspondre, et `createdAt <= now < expiresAt`. Le repository applique la mutation, écrit le reçu terminal, puis la composition renseigne `consumedAt`. Un commit unique conserve ces trois effets. Un rejet métier durable consomme également le grant et conserve son reçu dans ce commit. Une erreur ou interruption avant commit annule les trois effets. Aucun Argon2id ni transaction Prisma imbriquée sous verrou.

La concurrence conserve le protocole 4.2B/4.3B et ses délais : verrou une seconde, requête trois secondes, transaction cinq secondes, isolation Read Committed. Les décisions sont prises après acquisition du verrou. Deux consommateurs ne peuvent appliquer deux mutations ; le second ne peut que retrouver le reçu correspondant. Une révocation committée avant l'acquisition du verrou refuse la consommation ; une requête déjà autorisée avant révocation ne peut être annulée rétroactivement. Les écritures administratives qui ignorent ce protocole restent hors garantie.

## Réponse perdue et limites

Un grant consommé permet exclusivement de retrouver le reçu exact de son opération sous une session actuellement valide et son appareil non révoqué ayant toujours un `authorizedAt` non nul. Cette lecture de résultat est permise après expiration du grant ou changement de révision ; elle ne permet aucune nouvelle mutation. Le mode récupération consulte seulement un reçu existant, valide son identité et son empreinte avec la clé HMAC historique du reçu. Une absence de reçu interdit l'exécution : le garde `replayOnly` précède `apply`, donc aucun chemin de publication n'est appelé. Ni coffre, ni vérificateur, ni grant, ni reçu ne sont modifiés. Une requête différente est rejetée ou reçoit `IDEMPOTENCY_MISMATCH`, sans écriture. Le rejeu interne exige les mêmes données préparées ; il ne suppose jamais deux sorties Argon2id identiques après régénération.

La future couche HTTP devra lier durablement l'intention authentifiée aux données préparées pour reprendre après panne, limiter les tentatives avant Argon2id et maîtriser les erreurs et la divulgation des secrets. Il manque encore les endpoints, la préparation applicative complète, les règles de rétention et de limitation des grants et la qualification opérationnelle des horloges. Aucune procédure de révocation d'appareils n'est activée par ces grants ; un nouveau type nécessitera un contrat d'intention explicite, des contraintes et des tests propres.

Une session et un grant ne rendent jamais un appareil autorisé. `authorizedAt` reste un état serveur nécessaire mais ne prouve pas la possession cryptographique de l'identité E2EE ; SEC-CRYPTO-003 n'est pas implémenté. Les fixtures de succès renseignent ce champ uniquement dans les tests, sans procédure fictive de production. La limite atomique de cinq appareils de confiance et les rotations cryptographiques restent à SEC-CRYPTO-003. Le changement ordinaire conserve les autres sessions et appareils ; le reset par e-mail a une politique encore ouverte. La date de modification du vérificateur est depuis ajoutée par 4.4A ; son trigger suit les changements effectifs du PHC.

## Tests

Les tests rapides contrôlent la séparation des versions de jetons et leur format. Les tests réels PostgreSQL 18.7 appliquent toutes les migrations dans des schémas aléatoires de la base dédiée. Ils couvrent émission, mot de passe incorrect, erreur fournisseur, révision changée pendant KDF, expiration exacte, mauvaises liaisons et intentions, consommation concurrente, rollback avant commit, reçu durable, réponse perdue, recréation du client et révocations concurrentes. Les fixtures de publications sont structurelles, sans prétendre produire un parcours E2EE réel. Les scénarios utilisent plusieurs connexions. Les erreurs injectées testent les chemins d'échec ; l'atomicité est vérifiée dans PostgreSQL et ne repose pas sur une base simulée.

Modèle de menace : un grant volé seul est insuffisant sans sa session valide. Une session volée ne suffit pas à émettre un grant sans connaître le mot de passe. Le vol conjoint de la session et du grant permet son opération liée pendant sa validité ; les appareils compromis et un serveur actif pouvant capter le mot de passe restent hors de cette protection. Une fuite de base contient des empreintes de secrets aléatoires, sans protection contre la modification par un administrateur malveillant.

Qualification initiale avant corrections : 56 tests de persistance réussis sur PostgreSQL 18.7, dont 13 scénarios de réauthentification, avec migrations dans des schémas temporaires dédiés. La suite générale, typecheck, lint, format, build récursif, génération/validation Prisma et import ESM compilé ont réussi. Aucune qualification de production.

Après correction des frontières : 63 tests de persistance réussis sur PostgreSQL 18.7, dont 20 scénarios de réauthentification. Les nouvelles assertions couvrent la substitution entre deux PHC valides du même mot de passe avec sels distincts, les appareils en attente, la récupération sans écriture des deux états de reçu, le reçu absent, le HMAC historique, les mutations SQL interdites après consommation et le retrait concurrent de l'état serveur d'autorisation. La suite générale et toutes les vérifications du monorepo ont réussi sur ce code corrigé.

Une session expirée ou révoquée, ainsi qu'un appareil révoqué, produisent `INVALID_SESSION` après vérification sous verrou. Un appareil en attente ou un secret de grant incorrect produit `INVALID_GRANT`. Les erreurs transactionnelles non classées restent `OUTCOME_UNKNOWN` : ce code ne garantit pas un rollback après une défaillance de commit.
