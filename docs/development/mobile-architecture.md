# Architecture mobile — isolation des diagnostics cryptographiques

Cette page distingue l'architecture mobile actuelle des observations faites lors de jalons antérieurs. Le diagnostic HTTP local reste un outil de qualification, pas un transport métier. OpenE2EE 14.5.0 et le coffre V1 restent expérimentaux.

## Racines d'application

L'entrée standard `index.ts` installe d'abord `expo-crypto.getRandomValues` comme source globale, puis charge Expo et `src/product/App.tsx`. La racine produit est volontairement minimale et indépendante des diagnostics. L'entrée `qualification/crypto/entry.tsx` conserve le même ordre d'initialisation et compose l'écran de diagnostic. La configuration Expo active SQLCipher et SecureStore ; Metro conserve la résolution ESM de `jsonc-parser`.

- `qualification/crypto/composition` assemble l'écran et les scénarios expérimentaux. `qualification/crypto/diagnostics` contient les appels OpenE2EE, les stores SQLCipher/SecureStore, les témoins et les vecteurs JSON publics. La composition conserve une instance de fournisseur de coffre et de coordinateur Argon2id pendant la durée de vie du module ; le contrôleur reste propre à chaque montage.
- `src/infrastructure/crypto` conserve l'installation native de l'aléa, les adaptateurs natifs et le coordinateur Argon2id réellement réutilisés par la qualification. Leur présence commune ne les qualifie pas pour des données produit. `src/infrastructure/http` garde les transports partagés ; le diagnostic de santé HTTP local a été déplacé dans la qualification.
- Les scénarios crypto sont composés uniquement par `qualification/crypto/entry.tsx`. Les tests statiques et exports Metro vérifient que les graphes des deux entrées sont distincts et que les vecteurs et OpenE2EE sont absents de l'entrée standard. Ces graphes prouvent la résolution JavaScript observée par Metro ; ils ne démontrent pas quels modules natifs se trouvent dans un APK ou un Mach-O.
- Les packages partagés ne dépendent pas du mobile. Les tests contrôlent cette direction, l'import de l'écran, l'absence de cycles locaux et l'ordre d'initialisation de l'aléa.

Les noms de bases, clés SecureStore, options SDK, formats et étapes de diagnostic sont conservés. Aucun mécanisme de suppression ou de réinitialisation n'est ajouté. Les résultats historiques des qualifications demeurent dans leurs rapports respectifs ; ce déplacement ne requalifie pas la persistance après redémarrage Android, iOS ou production.

## Extensions

Les futures fonctionnalités pourront être ajoutées sous `features` lorsque leurs besoins seront définis, avec des ports explicites là où une frontière technique ou de sécurité le justifie. Aucun domaine vide ni conteneur de dépendances n'est anticipé. Avant de réutiliser les adaptateurs ou scénarios pour des données réelles, leurs contrats, leur persistance et leur sécurité devront être conçus et qualifiés ; SEC-CRYPTO-002 et SEC-CRYPTO-003 restent ouverts.

## Diagnostic HTTP local — résultat historique du jalon 4.5B1

La composition injecte une action de diagnostic dans l'écran. Le scénario traduit les catégories du transport en messages sans détails internes ; `infrastructure/http` effectue uniquement le GET de santé. Les autres diagnostics et leurs stores restent inchangés. Un verrou synchrone dans l'écran empêche les lancements concurrents, même avant le prochain rendu.

L'adresse `http://10.0.2.2:3000/health/live` est réservée au développement sur l'émulateur Android standard : elle désigne l'hôte depuis cet émulateur. Le diagnostic exige `__DEV__`, Android et une empreinte système reconnue `google/sdk_gphone…` ou `generic/sdk_gphone…`. Cette empreinte est un filtre conservateur, pas une preuve de sécurité : certains émulateurs peuvent être refusés et une empreinte peut être falsifiée. Les appareils physiques, iOS et la production ne disposent d'aucune configuration d'API dans ce jalon. La production ne reprend pas cette URL ; son réseau et TLS restent à concevoir séparément.

Le transport limite l'ensemble de la requête et de la lecture JSON à cinq secondes, demande l'annulation via `AbortController`, et retourne même si le transport ne réagit pas à l'annulation. Il demande `credentials: 'omit'`, n'ajoute ni authentification ni données et exige exactement le statut 200 et l'objet JSON `{"status":"ok"}`. React Native utilise un polyfill `fetch` dont l'option de refus des redirections n'est pas prise en charge : le transport natif peut suivre une redirection, mais une URL finale différente, lorsqu'elle est fournie, est refusée. Aucun secret n'est fourni à la requête. Les erreurs réseau, délai, statut et contenu sont distinguées sans afficher la réponse ni les exceptions. Les tests Node utilisent un transport simulé : ils ne prouvent pas le comportement réseau natif ou l'annulation effective sur Android.

Le projet Android généré localement contient `android:usesCleartextTraffic="true"` dans les manifestes des variantes `debug` et `debugOptimized`. Aucun changement natif n'a été apporté. Le manifeste de l'APK debug présent localement, examiné avec `aapt`, confirme également cette permission sans `networkSecurityConfig` ; son identité avec l'APK installé reste à vérifier sur l'émulateur ; l'accès à ADB était indisponible lors de cette implémentation. Le résultat Chrome ne prouve pas la politique du processus de l'application. Si l'APK installé refuse HTTP, déterminer sa variante et son manifeste fusionné avant tout changement ; une modification native impliquerait une reconstruction. Ne pas étendre cette permission à la production.

Le développeur a confirmé sur l'émulateur Android 17 que le Development Build Bunny Talks affiche une connexion réussie lorsque NestJS est disponible et un échec compréhensible lorsque l'API est arrêtée. La communication a ainsi été observée depuis React Native ; le succès précédemment constaté dans Chrome Android ne constituait pas cette vérification.

Les vérifications automatisées ont réussi : 36 tests mobiles avec transport simulé, vérifications du monorepo (`pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm format:check`) et export Metro Android. Les simulations ne démontrent pas l'annulation native effective.

Restent ouvertes : l'annulation effective au niveau natif, la désactivation et le comportement Android pendant une requête volontairement lente, ainsi que, si nécessaire, la vérification détaillée du manifeste de l'APK installé. Les diagnostics préexistants restent à requalifier selon leurs procédures respectives. La sécurité et la configuration du futur client HTTP de production restent à définir et qualifier ; ce diagnostic local ne constitue pas une qualification de production.

## Isolation des diagnostics cryptographiques

**État après l’étape C.** `index.ts` enregistre la racine produit minimale ; `qualification/crypto/entry.tsx` enregistre l'écran diagnostique et installe l'aléa avant de charger Expo. Pour exporter la qualification JS avec Metro, passer explicitement `--entry-file qualification/crypto/entry.tsx` à `expo export:embed`. Aucun import différé, contrôle `__DEV__` ou bouton masqué ne porte la séparation.

1. Garder `index.ts` comme entrée standard et lui faire assembler une racine produit indépendante des imports de qualification. Monter `DiagnosticsScreen` et ses scénarios dans une entrée Expo explicite sous `qualification/`, sélectionnée à la construction de l’artefact de qualification. Réutiliser l’initialisation de l’aléa, les adaptateurs natifs, le fournisseur Argon2id, les composants communs et les API/format V1. La chaîne standard doit pouvoir résoudre ses propres modules sans inclure les vecteurs de test. Une condition d’affichage ou un import différé dans le graphe produit ne garantit pas cette exclusion.
2. Construire la qualification crypto sous `fr.bunnytalks.mobile.cryptoqualification`. Les applications HTTPS conservent leurs identifiants propres. La future migration réutilisera le conteneur synthétique B1 avec le même utilisateur Android et une signature compatible.
3. Préserver le répertoire SQLite par défaut d’Expo et les fichiers `bunny-diagnostic-a1.db`, `bunny-diagnostic-a2.db`, `bunny-diagnostic-b.db` avec leurs éventuels fichiers associés. La fixture claire séparée est `bunny-diagnostic-plaintext-fixture-v1.db`. Pour chaque store chiffré, OpenE2EE 14.5.0 associe au nom `signal_protocol_sqlite_key.<fichier>` et réserve `signal_protocol_sqlite_pending_key.<fichier>` à la reprise d’une conversion. Conserver les options SDK, dont `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` sur iOS, ainsi que le service SecureStore par défaut de la version déclarée (`app` sur iOS, `key_v1` sur Android). Les clés manquantes ou erronées doivent produire un refus et préserver le fichier.
4. Les témoins et publications du diagnostic restent associés à leurs stores. Le [protocole de migration synthétique](android-crypto-synthetic-migration.md) décrit les comparaisons à effectuer avant les nouveaux échanges. Les scénarios de clé perdue ou incorrecte et de base claire utilisent des fixtures dédiées.
5. Le témoin OCR produit de Release est le nom de marque « Bunny Talks », indépendant des diagnostics. Le contrôle conserve le témoin négatif avant lancement, le rendu après lancement et la stabilité du PID. L'inspecteur de Release attend désormais `src/product/App.tsx` et refuse les sources de qualification ainsi que les marqueurs connus de l’SDK et des vecteurs. Cette inspection ne remplace pas l'examen de chaque binaire natif.

## Configurations d'identité crypto

La configuration standard conserve `fr.bunnytalks.mobile`. `BUNNY_CRYPTO_QUALIFICATION=synthetic` sélectionne `fr.bunnytalks.mobile.cryptoqualification`. Le prebuild applique cette identité et le script Gradle la vérifie avant de sélectionner l’entrée de qualification. Les réglages historiques sont refusés. L’[investigation B2-A](android-crypto-historical-b2a.md) conserve la provenance de l’APK historique et les limites observées à l’ouverture des stores. Le profil Android `initialization` sélectionne `fr.bunnytalks.mobile.cryptoinitialization`. Il réutilise l’entrée de qualification. Seule sa résolution Metro charge la composition d’initialisation avec les capacités Expo expérimentales. Les deux autres graphes gardent leurs entrées et les exports Metro ont vérifié leur séparation. [Jalon 3A](current-milestone.md).

## Nettoyage ciblé C

Le code propre au candidat historique a été retiré. Les scénarios synthétiques et tests de confinement continuent d’utiliser les adaptateurs et dépendances de qualification. L’autolinking natif et les usages de qualification justifient de conserver SQLCipher, SecureStore, Argon2id et le fournisseur d’aléa malgré la racine produit minimale. Les formats expérimentaux utilisés, vecteurs indépendants, tests de migration et l’alias OpenE2EE 14.4.0 restent nécessaires aux comparaisons. Aucun autre orphelin n’a été confirmé.

Les exports Metro Android de C comptent 586 modules pour `index.ts` et 1 029 pour `qualification/crypto/entry.tsx`, comme les builds B1. Les cartes de sources confirment que le graphe produit contient sa racine et exclut la qualification et le SDK. Le graphe synthétique contient le SDK et ses diagnostics, sans la racine produit ni le classifieur et l’écran historiques qui figuraient dans le bundle B2-A. Cette vérification porte sur le graphe JavaScript. Les preuves natives restent celles de B1.
