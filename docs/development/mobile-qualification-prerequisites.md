# Qualification mobile — prérequis et état de la migration

**État mobile au 14 novembre 2026 : qualification non validée.** L'examen préalable a révélé une correction de sécurité en OpenE2EE 14.5.0 qui concerne directement l'identité commune. La migration Node vers 14.5.0 a depuis été autorisée et réalisée ; ses résultats figurent dans le [rapport de migration](open-e2ee-14-5-migration.md). Une fondation Expo de diagnostic est désormais préparée ; la [qualification mobile](mobile-open-e2ee-qualification.md) reste non validée faute d'exécution native.

## Comparaison OpenE2EE

Au début de cet examen, le dépôt utilisait 14.4.0 ; le moteur utilise désormais 14.5.0, avec 14.4.0 isolée comme dépendance de test. L'archive npm officielle 14.5.0 a d'abord été téléchargée séparément pour lecture, avant son installation lors de la migration. Son journal indique que 14.4.0 pouvait accepter et épingler l'identité fournie par le relay pour un autre appareil du même compte, puis lui envoyer des copies de synchronisation et des clés de groupe. 14.5.0 compare cette identité à l'identité locale et refuse l'appareil divergent. La correction traite aussi une épingle propre périmée en remplaçant l'identité épinglée et en supprimant les sessions associées pour les rétablir. Sous Node, les tests Bunny Talks ont confirmé le refus de la substitution et le rétablissement d'une session légitime après remplacement d'une épingle périmée. Les limites, notamment les groupes non testés, sont détaillées dans le [rapport de migration](open-e2ee-14-5-migration.md).

Le POC Node 14.4.0 a démontré ses échanges dans les conditions de sa fixture ; il n'a pas testé cette substitution d'identité et ne démontre donc pas la protection corrigée. La correction ne prouve pas à elle seule l'authentification du relay ni l'autorisation d'un appareil. La migration 14.5.0 est validée pour poursuivre les expériences Node après revue ; la qualification mobile reste à réaliser. La [publication officielle](https://github.com/open-e2ee/signal-protocol-js/releases/tag/v14.5.0) renvoie au comparatif des versions ; l'analyse détaillée ci-dessus provient du `CHANGELOG.md` de l'archive 14.5.0.

Le journal annonce également des corrections de rejeu avec certificat expiré, de disponibilité des envois de groupe et de négociation relay. Il annonce un retour possible vers 14.4.0 pour le stockage, avec des limites sur le rejeu ; ce n'est pas une migration testée ici. Les listes de sous-chemins exportés et les plages de dépendances déclarées des deux manifests sont identiques. Cela ne démontre pas l'absence de changements de types ou de comportement. Les README de l'adaptateur Expo sont identiques ; aucune migration Expo n'a été exécutée.

Le fichier de génération de registration ID est identique entre les archives et la constante maximale 14.5.0 reste 16380 : la divergence précédemment observée ne peut pas être considérée comme corrigée. Les tests rejoués en 14.5.0 confirment la persistance SQLCipher et l'échec de `SessionRecord.serialize` sur une session réelle contenant un `bigint`. SEC-CRYPTO-002 et SEC-CRYPTO-003 restent ouverts.

## Plateforme et limites

Node 24.22.2 et pnpm 10.34.9 sont présents. Aucun `java`, `adb`, `emulator`, `sdkmanager`, `gradle` ou `xcodebuild` n'a été trouvé dans le PATH ; aucun SDK Android n'a été trouvé aux emplacements locaux examinés. Cela ne prouve pas l'absence d'un appareil ou d'une installation externe accessible autrement. Aucune compilation native, exécution Hermes, session mobile, mesure, fermeture ou réouverture SQLCipher mobile n'a été réalisée. iOS exige un environnement macOS et Xcode approprié.

La documentation installée de 14.5.0 indique les minima Expo 55.0.27, React Native 0.83.6, `expo-sqlite` 55.0.17 et `expo-secure-store` 55.0.15. L'adaptateur public exige un build natif avec SQLCipher ; Expo Go ne suffit pas. Il indique utiliser SecureStore par défaut pour la clé de base et refuser l'ouverture chiffrée sans SQLCipher ou lorsque la clé d'une base existante manque. Ce sont des contrats documentés, non des observations mobiles. Le choix exact d'un ensemble de versions compatibles, le fournisseur d'aléa et le comportement Hermes restent à qualifier dans la version retenue.

## Proposition historique ayant conduit au jalon de migration

Privilégier l'évaluation de 14.5.0 : examiner les changements publics, ajouter un test adversarial de substitution d'identité propre et un test de session après remplacement d'une épingle, puis rejouer les POC Node et contrôler les migrations avant qualification native. Une mise à jour doit rester explicite et ne pas être interprétée comme une validation de sécurité. L'alternative est de poursuivre une qualification 14.4.0 strictement expérimentale en documentant cette limite, au prix probable d'une seconde qualification après migration.
