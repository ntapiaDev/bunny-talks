# CRYPTO-009 — Prérequis techniques du coffre direct V1

**Statut : investigation et caractérisation Node, pour revue ; aucune API de coffre ni dépendance de production ajoutée.** Le [format V1](recovery-vault-direct-v1.md) reste candidat. Aucun résultat ci-dessous n'établit la compatibilité Hermes, Expo ou la sécurité de l'intégration complète.

## Parseur et canonisation : candidats distincts

Les candidats ci-dessous ne sont pas installés ni exécutés dans le monorepo. Les versions indiquées sont celles dont les manifests ou tags publics ont été examinés, pas nécessairement les dernières versions publiées. Leurs garanties concrètes, l'intégrité des distributions et leur maintenance devront être vérifiées avant toute sélection.

**Stratégie recommandée à évaluer**, pas une implémentation approuvée : limiter d'abord les octets reçus ; décoder avec un UTF-8 fatal éprouvé ; utiliser un parseur à événements configuré en JSON strict pour détecter les noms décodés dupliqués, refuser tableaux et profondeur interdite et arrêter tôt aux limites ; rejeter les erreurs, Unicode invalide, types et champs hors schéma. Ensuite appliquer un sérialiseur JCS conforme et comparer exactement les octets canoniques à l'entrée. Les contrôles de Base64url, tailles décodées, compte et profil précèdent la dérivation. `JSON.parse` seul perd les doublons et `JSON.stringify` seul ne trie pas les clés JCS. Un plafond d'entrée ne garantit pas à lui seul une profondeur ou une allocation bornées : démontrer quand le parseur alloue et peut s'arrêter. Le cas ASCII restreint V1 ne dispense pas de vérifier la conformité et les entrées invalides.

Avant adoption : tests de doublons simples et échappés, UTF-8 malformé, substituts isolés et paires valides, BOM, erreurs, valeurs numériques, commentaires, données tronquées, profondeur et bornes, vecteurs officiels RFC 8785, fuzzing, différentiel avec une implémentation indépendante, V1, Node et Hermes. Les tests existants caractérisent les API natives Node, pas les candidats ci-dessus ; **aucun vecteur officiel JCS n'a été exécuté contre un candidat dans ce jalon**.

## Aléa : chemins et défauts de sécurité

- **Node 24** : [`node:crypto.randomBytes`](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptorandombytessize-callback) et Web Crypto `getRandomValues` sont des API candidates ; les tests locaux exercent `globalThis.crypto.getRandomValues` via Noble, pas l'entropie ni les environnements mobiles.
- **Noble 2.4.0** : ses exports publics `@noble/ciphers/utils.js` et `@noble/hashes/utils.js` fournissent `randomBytes`, qui cherche `globalThis.crypto.getRandomValues`, échoue si absent et relaie les erreurs du fournisseur. Cela ne vérifie pas la qualité d'un polyfill installé sous ce nom ; un faux CSPRNG peut se présenter comme une fonction valide. La disponibilité ne prouve pas l'entropie. Son plafond par appel est de 65 536 octets dans le code installé.
- **Expo** : la [documentation SDK 55](https://docs.expo.dev/versions/v55.0.0/sdk/crypto/) décrit `getRandomValues` et `getRandomBytesAsync` comme utilisant des sources cryptographiques natives ; elle indique aussi que **`getRandomBytes` synchrone peut utiliser `Math.random` en développement**. Ce chemin est incompatible avec notre exigence, même pour un Development Build. La version Expo réellement retenue par l'application et ses modes de débogage sont à vérifier dans son code et sur appareils ; aucune absence de repli n'est déduite du seul nom d'API.
- **Polyfill React Native** : dans la [branche source examinée](https://github.com/LinusU/react-native-get-random-values/blob/master/index.js), `react-native-get-random-values` utilise ExpoCrypto quand disponible, mais comporte un repli `Math.random` dans un mode de débogage Chrome. Le global est aussi installé seulement s'il manque. Ne pas l'adopter automatiquement : vérifier la version exacte, l'ordre d'initialisation, le chemin effectivement exécuté et refuser toute configuration où ce repli est possible. Cette observation concerne la branche consultée, pas toutes les versions.

Recommandation : concevoir un fournisseur explicite, initialisé et vérifié avant toute opération, fondé sur une API native documentée sans repli faible dans **tous** les modes acceptés ; échec fermé si absent, erreur ou mode non vérifié. Un test qui reçoit des octets ne prouve jamais l'entropie ni l'absence d'un repli. Comparer l'appel explicite Expo `getRandomBytesAsync` et `getRandomValues` après inspection de la version effective et essais iOS/Android, plutôt que d'approuver un polyfill global par défaut. Le fournisseur et ses dépendances restent à décider.

## Noble et architecture

`@noble/ciphers` et `@noble/hashes` sont déclarés en **devDependencies 2.4.0**, MIT, ESM, Node ≥ 20.19, sans dépendance d'exécution déclarée dans leurs manifests installés. Les exports publics examinés sont `@noble/ciphers/chacha.js` pour `xchacha20poly1305`, `@noble/hashes/hkdf.js` et `@noble/hashes/sha2.js` ; leurs imports Node et les vecteurs CRYPTO-008 fonctionnent. Les imports Metro, l'initialisation d'aléa, `TextDecoder` fatal et les polyfills Hermes restent à tester. Les copies temporaires, le JIT et le ramasse-miettes empêchent de promettre effacement complet et temps constant. Les audits antérieurs des projets ne valident pas notre composition, notre version entière ni les plateformes. Ne pas promouvoir ces dépendances automatiquement en production.

Une responsabilité `crypto/backup` devient **justifiée conceptuellement** par la protection générique, les formats et le cycle de vie de sauvegarde ; son API, son graphe de dépendances et sa création restent à approuver. `crypto-core` conserve seulement les contrats de domaine réellement partagés, sans SDK ni infrastructure ; `crypto-engine` garde l'adaptation OpenE2EE et la validation des identités ; le futur coffre générique et la composition de la charge d'identité restent séparés. Les plateformes fournissent l'aléa et le stockage à travers des frontières à définir. Aucun package n'est créé.

## Résultats et points bloquants

`recovery-platform-characterization.test.ts` confirme sous Node que `JSON.parse` écrase les doublons simples et échappés, qu'un décodage UTF-8 fatal rejette des octets invalides, que `JSON.parse` accepte un substitut isolé, que `JSON.stringify` ne trie pas les clés et qu'aucune limite applicative de taille n'est fournie automatiquement. Il caractérise aussi, pour les deux exports Noble d'aléa, source présente, absente, erreur du fournisseur et limite de taille. Les tests ne démontrent ni un parseur sécurisé, ni la qualité de l'aléa mobile. Les vecteurs CRYPTO-008 restent dans la suite existante.

**Blocages avant API de coffre sûre :** choix et essais d'un parseur/canonicaliseur, vecteurs JCS et limites réellement appliquées, sélection et validation du CSPRNG et de sa chaîne native en modes réels, décision sur les dépendances et le package, spécification des interfaces, tests Expo/Hermes et revue de sécurité. Le contrat de fraîcheur, publication, reprise et charge d'archive reste ouvert. **SEC-CRYPTO-002 et SEC-CRYPTO-003 restent ouverts et bloquants avant production.** Ne pas commencer CRYPTO-010 sans revue.
